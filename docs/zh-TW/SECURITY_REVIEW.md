# 安全審查

[English](../SECURITY_REVIEW.md) | **繁體中文**

**這是什麼：** 由開發者（與 AI 助理一起）對 ProcLens 1.0.0 所做的結構化審查。它找出了真正的缺陷，全部已修正並有回歸測試涵蓋。
**它不是獨立稽核，也不是滲透測試**，其涵蓋範圍與限制已於第 5 與第 6 節如實說明。本審查所檢驗的設計決策，請見 `SECURITY.md`。

嚴重程度是審查者依預期使用情境（操作者在與其他使用者共用的機器上，檢視並傾印自己的處理程序）對「影響 × 可能性」的自行判斷。

## 1. 範圍與威脅模型

ProcLens 處理兩種敏感的東西：**其他處理程序的記憶體副本**（傾印），以及管理它們的**記錄與原則**。它是本機、無特權的工具；絕不自行提升權限。

| 攻擊者 | 假設的能力 | 可能的企圖 |
|---|---|---|
| A. 機器上的另一位一般使用者 | 可在任何人可寫的位置建立檔案（例如 `C:\ProgramData`、`C:\Users\Public`、`/tmp`），無法讀取操作者的設定檔 | 植入操作者的 ProcLens 會採信的原則或資料檔；讀取或竄改傾印 |
| B. 惡意檔案 | 交給 ProcLens 的精心構造的傾印、中繼資料、原則、稽核行或處理程序名稱 | 使其當機、耗盡記憶體／CPU、偽造輸出、欺騙解析器 |
| C. 惡意處理程序 | 名稱、路徑或擁有者含有控制字元、標記或形似文字的處理程序 | 注入報告、記錄與檔名 |
| D. 以*相同*使用者執行的惡意程式 | 操作者能做的一切 | **範圍外**：即使沒有 ProcLens，它也能讀取相同的處理程序與相同的 DPAPI 金鑰 |
| E. 本機系統管理員 | 完全控制 | 就機密性而言**範圍外**；僅與稽核記錄和原則所能證明的內容相關 |

## 2. 方法

1. **相依性檢查**：對全部 13 個專案執行 `dotnet list package --vulnerable --include-transitive`。
2. **靜態分析**：啟用所有規則的 .NET 分析器，檢視安全相關的規則族（CA2xxx、CA3xxx、CA5xxx），並搜尋有風險的 API
   （建立處理程序、反射載入、unsafe／舊式序列化器、弱演算法、原始記憶體存取）。
3. **人工審查**每一個信任邊界：傾印管線、金鑰處理與加密器、授權、稽核記錄、原則與保留、檔案建立、原生互通、不受信任輸入的解析器、
   報告轉譯、安裝程式。
4. **動態探測**，把懷疑變成證據：以一般使用者身分植入檔案、對 32 個惡意命令列做穩健性掃描、含記憶體量測的 572 MB 中繼資料檔、
   在真實 Linux 核心上的符號連結測試，以及金鑰推導上限的計時。
5. **回歸測試**：每個發現都有，並盡可能寫成在修正前會失敗。

## 3. 結果總覽

| 檢查 | 結果 |
|---|---|
| 已知有弱點的套件 | 無，全部 13 個專案（直接與間接相依）皆然 |
| 安全分析器（CA2xxx/3xxx/5xxx） | 沒有發現 |
| 產品程式碼中的風險 API | 無建立處理程序、無反射載入、無 unsafe／舊式序列化器、無 `unsafe` 程式碼；只使用 AES-GCM、SHA-256、PBKDF2-SHA256；`Random` 僅用於重試抖動 |
| 穩健性掃描（32 個惡意命令列：亂碼、截斷、超大、裝置名稱、把目錄當檔案、負數識別碼；一個 100,000 字元的引數因超過作業系統限制，連啟動都做不到） | 0 次當機（但見 F8：函式庫把堆疊追蹤隱藏在結束代碼 1 之後） |
| 發現 | 8 項，全部已修正（F1 到 F8）；其中 3 項在修正前已對執行中的程式碼實證 |

## 4. 發現

### F1（中，已修正）：本機原則檔可被任何使用者植入

*證據。* 在預設的 Windows 安裝上，`BUILTIN\Users` 可以在 `C:\ProgramData` 建立檔案與資料夾。一位未提升權限的一般使用者建立了
`C:\ProgramData\ProcLens\policy.json`，內容為 `Retention.MaxAgeDays = 0` 與 `AdminDumpsEnabled = true, RequireReason = false`。
ProcLens 接受了它：`dump prune` 隨後選取了一份兩天前的傾印要刪除，而系統管理員理由的規則也被削弱。任何執行排程 `dump prune --delete` 的人
都會失去他們的傾印；系統管理員關卡本來也應該是*系統管理員*的決定。

*修正。* 只有在一般使用者不可能寫入該原則檔時才會採信（`PolicyFileTrust`）：在 Windows 上，檔案與其資料夾的擁有者必須是 Administrators、SYSTEM 或
TrustedInstaller，且沒有任何其他人擁有可修改、取代、刪除或接管兩者的權限（允許建立子資料夾；僅繼承的項目不算）。在 Unix 上，兩者都不可被群組或其他人寫入。
不受信任的原則會被**忽略**：系統管理員傾印維持停用，保留使用預設值，並由 `proclens policy show` 說明原因。以 `PROCLENS_POLICY` 指定的路徑是操作者自己的明確決定，
因此被信任。修正後重跑同一個攻擊：被植入的檔案被忽略。

*測試。* 以合成 ACL 對該判斷做 16 個資料驅動案例與數個事實案例；以及真實 ACL 的對照（Windows 系統檔案被信任、使用者建立的檔案被拒絕、
植入 `C:\Users\Public` 的原則端到端被忽略）。

### F2（低到中，已修正）：中繼資料與原則檔沒有大小限制

*證據。* 傾印旁邊一個 572 MB 的 `.json` 讓 `dump prune`（試執行）使用了 **2,907 MB** 記憶體（基準為 30 MB）。植入共用傾印資料夾的檔案，
可能耗盡執行 `prune` 或 `report --dumps-dir` 者的記憶體。

*修正。* 大於 1 MiB 的中繼資料與原則檔不會被讀取（真實檔案約 1 KB）。

### F3（低到中，已修正）：安全刪除會寫穿符號連結

*證據。* 在 Ubuntu 24.04（真實核心）上，對指向 `precious.txt` 的符號連結執行 `SecureDelete`，刪除了連結**並以零覆寫了目標**
（29 位元組，全為零）。保留機制在掃描時會略過連結，但在掃描與刪除之間被換進來的連結，或任何其他呼叫端，都可能造成別的檔案被毀。

*修正。* 重新解析點（reparse point）只會被移除，絕不會被開啟寫入。測試在 Linux 上執行。

### F4（低，已修正）：金鑰推導上限過於寬鬆

精心構造的加密檔可以為最多 8 個密碼槽各自指定 PBKDF2 迭代次數。在舊的上限（10,000,000）下，一個槽約耗用 1.3 秒 CPU，
因此開啟一個惡意檔案可能燒掉約 10 秒。上限現在是 3,000,000（預設值 600,000 的 5 倍），並在做任何工作之前就拒絕；以預設值寫入的檔案仍可讀取。

### F5（低，已修正）：輸出路徑可寫入替代資料流或裝置

*證據。* `report generate --output <目錄>\a:b.txt` 回報成功，並悄悄地把報告寫進名為 `a` 的檔案的 NTFS 替代資料流。路徑是操作者選的，
因此這比較像是意外而非攻擊，但隱藏資料流正是隱藏資料的經典手法。

*修正。* 對每個會寫入檔案的指令，`OutputPathPolicy` 都會拒絕：磁碟機代號以外的冒號、DOS 裝置名稱（`CON`、`NUL`、`COM1` 等，無論有無副檔名）、
裝置路徑（`\\.\`、`\\?\GLOBALROOT`）與控制字元。套用於 `dump create --output`、`dump decrypt/export --output` 與 `report generate --output`。

### F6（對誠實性屬中，已修正）：稽核雜湊鏈被描述得比實際更強

雜湊鏈使用無金鑰的 SHA-256。它能抓出損壞與草率的編輯（任何單一筆編輯、插入、刪除或重新排序都會破壞它，已測試），但是**任何能寫入該檔案的人都能一致地重算整條鏈**，
而沒有東西能偵測到，從結尾截掉記錄也看不出來。先前的文件說編輯「會被偵測到」，卻沒有這項但書。

*修正。* 文件現在明確說明這項限制。`audit verify` 會印出檔頭雜湊並接受 `--anchor <hash>`：事先存放在記錄寫入者碰不到之處（工單、另一台主機）的檔頭雜湊，
可證明之前沒有任何內容被改寫、沒有任何內容被截掉。測試包含一份完全重建、內部有效的偽造，它能通過一般檢查，卻無法通過錨點檢查。

### F7（低，已修正）：`dump export` 複製加密區塊時沒有檢查

匯出會重新包裝金鑰並原樣複製區塊，因此受損或被修改的傾印會被毫無怨言地匯出，直到最後開啟時才失敗。現在會在寫入任何東西之前，
先端到端驗證來源（並與其記錄的原始雜湊比對）；失敗時不會建立任何東西。

### F8（低，已修正）：未預期的失敗會印出堆疊追蹤；原生回呼中的例外會使處理程序當機

*證據。* System.CommandLine 的預設處理常式會攔截指令的例外並將**完整堆疊追蹤**印到標準錯誤；對於用法錯誤，它還會把整個說明頁印到**標準輸出**，
這會破壞讀取 `--json` 的指令碼。

*修正。* 未預期的錯誤現在只給一行（`Unexpected error (Type): message`）並以結束代碼 70 結束；完整細節可用 `PROCLENS_DEBUG=1` 取得。
用法錯誤只輸出到標準錯誤。DbgHelp 取消回呼內的例外會被攔截，並中止那一次傾印，而不是終止處理程序。

## 5. 殘餘風險（已接受或未解決）

| 風險 | 狀態 | 原因 |
|---|---|---|
| **原始傾印會短暫地存在於磁碟上**，即加密前的 `*.dmp.plain.tmp` | 未解決，依設計 | `MiniDumpWriteDump` 需要檔案控制代碼。該檔案僅限使用者存取，並在加密副本驗證後被抹除並刪除，殘留的孤兒檔由 `prune` 移除。但備份／索引代理程式可能看得到它，而且覆寫並不保證在 SSD 上抹除。**真正的解法是經由 DbgHelp 的 I/O 回呼把傾印直接串流進加密器，使明文永不接觸磁碟；這點尚未嘗試。** |
| 以相同使用者執行的惡意程式 | 範圍外 | 即使沒有 ProcLens，也能讀取相同的處理程序並解除 DPAPI 主金鑰的保護 |
| 來自 `--password-env` 的密碼 | 已接受 | 環境區塊中的值可被同使用者的處理程序看到；受控字串的副本無法抹除（`SecretText` 的副本可以） |
| 擁有者比較使用帳戶*名稱*，而非 SID | 已接受 | 名稱是完整限定的（`DOMAIN\user`），而要製造形似的名稱需要系統管理員權限 |
| 預先存在的稽核記錄或金鑰檔不會被檢查是否有寬鬆的 ACL | 已接受 | ProcLens 建立它們時是私有的；它不會修復別人建立的檔案 |
| 輸出目錄的檢查時間／使用時間（TOCTOU）問題（先檢查連結，再使用） | 已接受 | 需要對父資料夾的寫入權限；所建立的目錄是私有的 |
| 稽核雜湊沒有金鑰 | 已緩解 | 搭配外部儲存的檔頭雜湊使用 `--anchor` |
| 沒有程式碼簽章；安裝程式未簽章 | 未解決 | 需要憑證；請驗證 `SHA256SUMS.txt` |
| 供應鏈：沒有套件鎖定檔，CI actions 以標籤而非 commit 固定 | 未解決 | 套件已固定到精確版本；可考慮鎖定檔與固定 action 的 SHA |
| `dump export` 的來源必須能在這台機器上解鎖 | 依設計 | 僅密碼的副本才是可攜格式 |

## 6. 本審查未涵蓋的範圍

- **以真正提升權限的權杖進行系統管理員傾印。** 授權邏輯有單元測試，拒絕情形也已觀察到，但成功路徑從未在提升權限下執行過。
- **macOS。** 沒有任何東西在那裡執行過。Linux 的檔案權限處理只在 Linux（WSL2）上測試過。
- **Windows ARM64 與 Linux ARM64。**
- **超出掃描與單元測試的模糊測試**（未對 minidump、容器或原則解析器做覆蓋率導向的模糊測試）。
- **旁路攻擊**（時序、記憶體殘留）。AES-GCM 與金鑰推導使用平台密碼學；ProcLens 不自行實作原語。
- **Protected Process Light 與防惡意程式的互動**：ProcLens 不會嘗試擊敗它們，而是回報存取被拒。
- **獨立審查。** 在 ProcLens 被託付於敏感環境之前，仍建議由另一雙眼睛、最好以不同方法再審一次。

## 7. 驗證

修正之後：450 個自動化測試在 Windows 上通過（另有 15 個因需要其他作業系統而略過），相同的測試套件在 Linux 上也通過（僅 Windows 的測試在該處略過）。
每個發現至少有一個回歸測試；F1、F2 與 F3 在修正前已對執行中的產品重現。
